## Current Milestone

**Sprite gallery tool + oval collision footprints (2026-07-25)** — Built and verified headless; **not yet Designer-playtested**, and the feel change wants one.
- **New standalone sprite browser** (`scenes/tools/sprite_gallery.tscn`, run with F6) — every image the game ships, grouped by category, without booting a battle. Cards preview at real draw scale using the field's own conventions (characters/props stand on a ground line, rocks/rings draw centred, all at `Combatant.SPRITE_ALPHA`), with toggles for a Thundaar size reference, the sprite's true opaque bounds vs. its collision shape, and the oval footprint. **The folder scan is authoritative and `assets/ASSET_INVENTORY.json` only annotates it**, so a PNG dropped into `assets/sprites/` appears immediately tagged `? unlisted` — the tool cannot silently disagree with the disk.
- **Asset audit** — all 44 PNGs catalogued (`assets/ASSET_INVENTORY.json`) with status and wiring, plus a working list in `ASSET_REPLACEMENT_CHECKLIST.md`. Every claim was grep-verified rather than assumed, which corrected two orphan reports: `Verdant_Path.png` (used by `plant_trail.gd`) and `Portal-Spawn.png` (used by `spawn_point.gd`) are both live, and `Arrow.png` turned out to be deliberately-kept source art for the pre-rotated `Arrow_Right.png`. Six files are confirmed stale at zero references; `Lightning-Bolt.png` and `Sprites.png` need a Designer call.
- **Found: collision circles were paying for transparent padding.** `_collision_radius()` spanned the sprite's *longest image edge*, so a tall character's collision WIDTH was set by his height (Thundaar's circle was ~1.4× wider than he is) and padded exports paid for empty pixels — `Berserk_Minion_1.png` is 59% empty on its long edge, and its `sprite_scale` of 3.6 looks like compensation for exactly that, which multiplied the waste.
- **Collision is now an OVAL derived from the opaque art** (`scripts/sprite_footprint.gd`). Ellipses reuse the existing circle math through a directional radius — the same trick `_lake_radius_toward` already used — so `obstacles` stays `Array[Vector3]`, there is no ellipse solver, and the change is confined to `Combatant._collision_radii()` plus `LaneField`'s three collision entry points. Thundaar 67 → 41×50, Artemis 67 → 35×57, Berserk minion 50 → 15×18.
- **The safety invariant: every footprint derives from the AUTHORED radius, never the drawn size**, so an oval can only reshape a blocker and never grow one (`rx, ry ≤ radius` always). That is what keeps every already-validated layout valid. Verified across all 9 unit sprites and all 42 obstacles in the three levels.
- **Walkability re-verified.** No BFS harness existed (that check had always been manual); wrote one that reads the `level_*_layout.tres`, derives each obstacle's oval exactly as `LaneField._footprint_for` does, and floods deploy→lair per lane using the real ellipse test. **All three levels clear both lanes.** Battlefield runs clean headless (the only exit warnings are a pre-existing menu-MP3 leak, confirmed by reproducing them independently).
- **Deliberately NOT done, with reasons:** *scenery* got no footprint because it has no collision at all (draw-only — walking through a smudge is correct per ART_BIBLE); *tall props* get a flat ground footprint at the trunk rather than an art-hugging oval, because the canopy is meant to overhang so units path around the trunk.
- **Known trade to watch:** spawn gates block at authored radius 44 but their portal art draws at 176px, so art already dwarfed collision there and the oval (~28×37) widens that gap slightly. Took the safe side since 44 is what layouts were cleared against. If heroes visibly overlap the portal art, normalize the gate's oval so its long axis stays 44 instead of shrinking below it.
- **Next:** playtest the feel — Stage 2's swarm loosens most. `SpriteFootprint.COVERAGE` (0.85) is the single knob and scales every unit and obstacle at once, so treat it as a balance number, not a visual tweak. Cropping the over-padded PNGs before further tuning would mean one feel shift to evaluate instead of two stacked.

**Duo system: explicit pairing, leader/follower choice, named synergy identity, targeting fix (2026-07-20)** — Built, Designer-confirmed working in-session (not yet a full engine/CLI verification pass — see flags below).
- **Duo Bonus (replaces Synergy + Formation):** the old opportunistic "any nearby hero" Synergy (+15% dmg/−0.3s CD/+25% XP) and role-based Formation proximity bonuses were unified into one system — `Hero._update_duo_bonus()` — active only when a hero has a *confirmed* Duo partner (`GameState.duo_pairings`) alive and within 200px (`DUO_DISTANCE`). Leader gets +15%/−0.3s/+25%; follower gets +10%/−0.2s/+15% (`DUO_LEADER_*`/`DUO_FOLLOWER_*` in `hero.gd`, first-pass numbers, not yet balance-tested).
- **Leader/follower is a pure player choice, not role-derived:** originally computed from a fixed role rank (TANK always led), which the Designer flagged as not fitting the new design ("tank always leads does not work anymore ... this should be a player decision, even when it does not seem to make sense"). Replaced with `GameState.is_duo_leader()` — whichever hero is dropped in a Duo's left/A prep-menu slot leads; right/B follows. Prep menu now labels each slot LEADER/FOLLOWER before a hero is even dropped in it.
- **Per-hero leader/follower behavior layer (deliberately small, keyed only on hero_name + leader-vs-follower, never on the partner's identity):** THUNDAAR leading gains attack speed + damage (`THUNDAAR_LEADER_ATK_SPEED_MULT`/`_DAMAGE_MULT`); following, he bodyguards — hard-overrides targeting to whatever is attacking the Duo leader (`_bodyguard_target`). ARTEMIS leading gains +25% max HP + faster Clone cooldown (`ARTEMIS_LEADER_HP_MULT`/`_CLONE_COOLDOWN_MULT`); following, she focus-fires whatever the leader is currently fighting (a target-score nudge, not a hard override, in `_role_bonus`'s new BURST case). WARDEN/BEACON have no extra layer yet — generic Duo Bonus only, flagged as an open gap, not silently skipped.
- **Removed as a wrong turn (caught mid-session):** an earlier per-partner-role tweak matrix (`_apply_duo_partner_tweaks`, Ensnare anchor-switching, Warden's cluster-search bias toward a SUPPORT partner) caused Warden's targeting to visibly conflict with itself depending on which specific hero she was paired with. Ripped out entirely per Designer direction ("It is fixing leader and follower to specific heroes... should not have a specific behavior for each hero... reduce scope creep") in favor of the small hero_name-keyed layer above.
- **Named Duo synergy identity (presentational only):** new `scripts/duo_synergies.gd` catalog — one entry per of the 6 possible role-pairs (name + description), same static-catalog pattern as `Achievements`/`AbilityMods`. Shown in the prep pairing panel (per-Duo card) and as a "DUO A/B: <name>" banner on the battle HUD while that Duo has a live hero on the field. **Names/descriptions are placeholders** pending Designer naming — flagged, not treated as final content.
- **Targeting fix — heroes were ignoring nearby minions to beeline a locked spawn point/villain:** the spawn-point (`SPAWN_POINT_ENGAGE_RANGE` 500px) and villain (`VILLAIN_ENGAGE_RANGE`) locks were absolute distance checks with no regard for what a hero was walking past. Two additive fixes in `Hero._acquire_target()`: (a) a tight "nearby swarm interrupt" bubble (`attack_range × 1.5`, floored at 90px) swats anything already adjacent before continuing toward any lock; (b) a broader "on the way" check — if an ordinary minion (new `_nearest_minion()`, excluding spawn points/villains) sits closer to the hero than the currently-locked gate/villain, the minion wins instead. Designer-confirmed this fixed the reported Warden beelining behavior.
- **Not yet verified via godot-ai MCP/CLI this pass** (Designer directed staying low on tool calls this session) — static code review + Designer live-playtest confirmation only. Recommend a `godot-ai` pass before the next balance sweep, specifically: Duo Bonus proximity gating, the leader/follower behavior layer under all 6 possible pairings, and the new targeting priority under real swarm density.
- **Next up (Designer-requested):** a `balance-qa` skill pass evaluating the whole Duo setup's numbers — Duo Bonus magnitudes (leader vs. follower split), the per-hero leader/follower stat bonuses (Thundaar atk-speed/damage, Artemis HP/Clone-CD), and whether the new "on the way" minion-interrupt meaningfully slows spawn-point clear times. None of the Duo-related numbers above have been through a sweep yet — first-pass guesses only.

**V2 lane-structure parallel testing build (2026-07-19)** — Built, pending Designer playtest. A side-by-side alternative structure, NOT a replacement — V1 is fully intact and both are playable back-to-back from the same build (prep menu → "V2 (LANE TEST)" button; V2 prep has a "BACK TO V1" button). Purpose: let the Designer *feel* whether the game needs a structural change.
- **Thesis:** the battlefield is a narrow horizontal lane (centered on origin, ~6000×900). Heroes deploy from a fixed band at the left end and push right toward the villain's dormant lair. Minion spawn points are distributed along the lane and are **destructible** — killing one permanently stops its waves. **Win = villain dead AND all spawn points destroyed.**
- **The one player verb is live redeployment** (no focus ping, no priorities, no pin): each hero has its own deploy timer, comes online staggered at the opening, and after death returns on a longer respawn cooldown. Each hero gets `MAX_LIVES` (3) deploys per level; **loss = every hero has exhausted its lives**. Grindier XP curve (`RunState.V2_XP_GRIND_MULT`).
- **Fork is small by design:** `LaneField extends StageField`, so every `Combatant` (heroes, all minions, all villains) is reused byte-for-byte via the inherited steering/collision API. `LaneSpawnPoint extends Combatant` (destructible gate) and `LaneSpawner` reuse the swarm loop. Reused unchanged: hero, combatant, minions, villains, fog, camera, HUD, results, level-up, boons, ability-mods, stage configs.
- **Own persistence:** V2 writes `user://save_v2.json` + `user://fog_v2/` via `GameState.v2_mode`; V1 data untouched. Only additive edits to shared files: `game_state.gd` (v2_mode + `save_path()`/`fog_dir()`/`prep_scene()` helpers), `fog_of_war.gd` (fog dir), `battle_hud.gd` (back button routes via prep_scene), `prep_menu.gd` (V2 button + resets context on load), `run_state.gd` (v2 grind mult).
